# AGENTS.md

## Style — DRY and reuse first

Follow the patterns already in the codebase rather than inventing new ones.
Be succinct!

## Project map

- `src/` and `src/include/`: C++20 simulation core; `src/cli/`: native CLIs.
- `python/apitofsim.cpp`: nanobind bindings; `python/apitofsim/`: Python API,
  Click CLI, configuration, ingestion, plotting, and DuckDB workflows.
- `python/apitofsim/workflow/sql/`: database schemas and report queries.
- `test/`: doctest C++ tests, pytest tests, fixtures, and benchmarks.
- `docs/development.md`: build/debug/profiling instructions; `docs/`: user docs.
- `meson/dev/`, `meson/test/`, and `meson/pkg/`: native build configurations.
- `.github/workflows/`: authoritative CI commands and platform coverage.

## Development

- Use uv and Meson/meson-python. Python requires 3.12+; native code requires
  Meson 1.10+, Eigen 3.4+, and oneTBB 2023.0+. See `docs/development.md`.
- Inspect the local `uv.toml` and existing build configuration before building:
  native files and build paths can be machine-specific. Do not overwrite them.
- `./uv_sync.sh` installs all dependency groups/extras and reinstalls the project.
  Editable installs rebuild native code on import.
- Keep core changes, bindings, Python wrappers/exports, and docs consistent.
  Type stubs are generated by the build; change their source rather than outputs.
- Justified breaking changes to APIs, CLI/config formats, and schemas are allowed.
  Update tests and docs, explain the break, and flag downstream impact.
- Parallel execution uses oneTBB. `OMP_NUM_THREADS` does not control it; remaining
  OpenMP SIMD pragmas are vectorization hints. Use existing concurrency patterns.
- Check consumers in sibling `apitofsim-resultviewer` and `apitofsim-web` when
  changing shared APIs or result schemas; report any required downstream changes.
- Preserve existing local data, simulation outputs, and unrelated untracked work.
  Use small test fixtures rather than committing generated databases or results.

## Local QA

Run QA locally before reporting work complete. For routine changes, run relevant
tests and language QA; broaden coverage for risky changes. Fix failures introduced
by the work, and report commands/results and any checks that could not run.
Do not use CI as the first validation step.

- Python lint/format: `uv run ruff check python` and
  `uv run ruff format --check python`; also check changed Python tests/scripts.
- Python types: follow `.github/workflows/qa.yml`: run basedpyright against the
  installed package with that environment's Python (including plot/notebook
  extras). Generated native stubs must be available. Type coverage via
  `--verifytypes apitofsim` is currently advisory in CI.
- Native and integrated tests: `./test.sh -C <build-dir>`; the script disables core
  dumps for intentional signal tests. Meson runs C++ tests at one-thread and
  default concurrency, plus registered Python tests when dependencies are present.
  Confirm Python tests were included rather than silently skipped.
- All Python tests: `DATA_DIR="$PWD/test/data" uv run python -X dev -m pytest test/`.
  Meson's explicit Python test list does not include every pytest file. Run the
  Meson suite too when signal-helper coverage is needed.
- C++ QA: build with warnings as errors, then run
  `ninja -C <build-dir> clang-format-check` and `ninja -C <build-dir> clang-tidy`,
  following the Clang configuration in `.github/workflows/qa.yml`.
- For native memory/lifetime/concurrency changes, use the sanitizer and Valgrind
  configurations under `meson/test/` as appropriate; see the test workflow.
- Docs changes: `PYTHONPATH=./python/ uv run --group docs zensical build --clean`.

## Pull requests and CI

When directed to open a PR, run local QA first, then open the PR and watch CI
through completion. After every fix/push, watch the checks for the latest commit
again. Inspect failure logs, fix failures caused by the changes, and repeat until
CI passes. Include all applicable workflows, including platform wheels and docs,
rather than stopping after one green job or after merely opening the PR.

If an external failure or missing access prevents completion, state the exact
blocker and outstanding checks. Do not claim the PR is ready while CI is pending
or failing.
